# GSM-20H10: is it the NUMBER of writes, or WHICH writes?
#
#   uv run tools/scpi_console.py --address <addr> \
#       --no-error-check --timeout 30 \
#       --script tools/probes/20h10_burst_length.txt
#
# Run only after the burst probe has reproduced the fault at least once.
# Until then there is nothing here to explain.
#
# Two readings of "the first query after a burst of writes":
#
#   FLOW CONTROL - the link cannot take N writes with no read between
#       them, whatever they say. Prediction: the failure tracks N and
#       does not care about content, so the inert block below fails at
#       roughly the same N as the real one.
#
#   THE INSTRUMENT IS BUSY - one particular command sets it thinking
#       (SYST:LFR:AUTO has to measure the mains; a range change moves
#       relays). Prediction: this file never fails, at any N, because
#       every write in it is inert.
#
# FORM:ELEM is the inert write: known-accepted on V1.16, changes one
# formatting flag, moves no hardware and starts no measurement.
#
# Each query below is the first after a burst of the stated length. The
# ones before it succeeded, so the link is warm - that biases toward
# NOT failing, which makes a failure here the strong result.
#
# Ten runs, as before. Note the N at which the first slow reply appears,
# not only the one that dies.

*CLS
SYST:CLE
