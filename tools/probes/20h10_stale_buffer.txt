# GSM-20H10: does the buffer hand back an earlier sweep's readings?
#
#   uv run tools/scpi_console.py --address <addr> \
#       --no-error-check --timeout 30 \
#       --script tools/probes/20h10_stale_buffer.txt
#
# *** THE OUTPUT COMES ON, 0 to 0.1 V at 100 uA compliance. Nothing
#     connected, or the cell. Default pacing - no --write-delay. ***
#
# Found by 20h10_doubled_sweep.txt, 2026-09-16: a 5-point sweep returned
# 10 readings, and readings 6-10 were identical to seven digits in three
# sweeps including one after *RST - 0.111, 0.333, 0.556, 0.778, 1.000 V,
# the tail of an earlier 10-point -1 V to +1 V sweep. TRAC:CLE,
# TRAC:POIN and *RST all left them there, and TRAC:POIN:ACT? counted
# them.
#
# The question that decides the fix, and whether IV sweeps already
# taken are sound:
#
#   RIGHT AFTER INIT, before the new sweep has had time to take its
#   readings, what do TRAC:POIN:ACT? and TRAC:DATA? say?
#
# If ACT? already reports the full count and DATA? returns the PREVIOUS
# sweep's values, an IV sweep of the same length as the one before it
# is read out before it has run: the poll loop sees 'done' at once and
# the file gets the last sweep's numbers. On the same cell with the same
# settings those look entirely right.
#
# Sweeps are slow on purpose (100 ms per point) so 'right after INIT'
# and 'after it finished' are far apart, and every sweep uses levels no
# other sweep here uses, so any value can be traced to the sweep that
# took it:
#
#   S2  10 points, 10-100 mV   - fills the buffer to 10
#   S3  10 points, 5-50 mV     - SAME LENGTH: the case that matters
#   S4  3 points, 70-90 mV     - SHORTER: expect S3's tail after it
#
# For S3, compare its 'early' ACT? and DATA? against S2's final data.
# The 150 ACT? lines show the count moving while each sweep runs; if the
# first takes about a second to answer, the instrument holds queries
# until the sweep ends, which would make early reads impossible.
#
# ONE RISK, ACCEPTED: if TRAC:CLE does empty the buffer, an early
# TRAC:DATA? on it may never answer, the link latches and the console
# stops there. That outcome is itself the answer - an early read cannot
# return stale data - and the lines before it say which sweep it was.

# ==== reset, as the app sends it at connect ====
*CLS
*RST
SYST:CLE
SYST:BEEP:STAT 1
OUTP:ENAB 0
SYST:LFR:AUTO 1
SOUR:CLE:AUTO 0
ROUT:TERM FRON
TRAC:FEED:CONT NEV
FORM:ELEM VOLT,CURR
SYST:ERR:ALL?

# ==== the buffer as found, and what TRAC:CLE does to its count ====
TRAC:POIN:ACT?
TRAC:DATA?
TRAC:CLE
TRAC:POIN:ACT?

# ==== voltage source at 0 V, 100 uA compliance, output on ====
SENS:FUNC:CONC ON
SENS:FUNC:ON "VOLT","CURR"
SOUR:FUNC VOLT
SOUR:CLE:AUTO 0
SOUR:VOLT:RANG:AUTO OFF
SOUR:VOLT:RANG 1.000000e-01
SENS:CURR:DC:RANG:AUTO OFF
SENS:CURR:DC:RANG 1.000000e-04
SENS:VOLT:DC:RANG:AUTO ON
SENS:CURR:DC:PROT:LEV 1.000000e-04
SENS:CURR:DC:RANG 1.000000e-04
SENS:CURR:DC:NPLC 0.0100
SENS:VOLT:DC:NPLC 0.0100
SOUR:VOLT 0.000000e+00
OUTP 1
SYST:ERR:ALL?
