# GSM-20H10: why does the checkup's 5-point sweep return 10 readings?
#
#   uv run tools/scpi_console.py --address <addr> \
#       --no-error-check --timeout 30 \
#       --script tools/probes/20h10_doubled_sweep.txt
#
# *** THE OUTPUT COMES ON, 0 to 0.1 V at 100 uA compliance - the
#     checkup's own levels. Nothing connected, or the cell. ***
#
# Seen 2026-09-16, all four checkups at 3c2164e: `TRAC:POIN 5`, a
# 5-point staircase, and `TRAC:POIN:ACT?` answering 10. On 2026-09-14 the
# same commands in the same order gave 5. The IV sweep in the app, paced
# the same way, gave 10 points for 10 - so the 5 ms pause alone does not
# double a sweep, and the suspect is state left by something the checkup
# does before it. The new tier 2 step ("a range wider than the old
# compliance survives the new one") is the only traffic added before the
# sweep since 09-14, so it is replayed here verbatim from the 14:11:50
# trace.
#
# Runs with the console's default pacing - the driver's 5 ms, the same
# as the app and the checkup. Do not add --write-delay 0: the sweep
# block is sixteen writes and a query, which is exactly the burst this
# instrument drops, and a latched link would end the probe before it
# answered anything.
#
# THREE SWEEPS, SAME BLOCK EACH TIME:
#
#   A  straight after a reset          - the control
#   B  after the new tier 2 step       - the suspect
#   C  after another reset             - does *RST clear it
#
# Read, for each: the TRAC:POIN:ACT? progression and the full TRAC:DATA?.
#
#   A=5, B=10, C=5   the new step leaves the state; *RST clears it
#   A=5, B=5         the step is not it - the next probe replays the
#                    whole checkup up to the sweep
#   A=10             it is the sweep block itself, as sent today
#
# The six TRAC:POIN:ACT? in a row are deliberate. The console sends them
# about 10 ms apart, so they show the count climbing. Stopping at 5 and
# jumping to 10 later means the staircase ran twice; climbing straight
# to 10 means one run of ten.
#
# The settings queries at the end of B come AFTER the data on purpose.
# TRAC:POIN?, TRIG:COUN?, ARM:COUN? and SOUR:SWE:POIN? have never been
# sent to this instrument. If one is not implemented it is never
# answered, the link latches and the console stops - so they go where
# losing the rest costs only C.
